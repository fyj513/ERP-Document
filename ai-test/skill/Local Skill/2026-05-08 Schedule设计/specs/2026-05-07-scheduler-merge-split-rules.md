# Scheduler 合并/拆分规则与优先级策略

> 回答用户核心问题：多SO合并时优先级怎么定？哪些Demand可合并、哪些必须拆分？

---

## 一、核心结论：不是所有Demand都能合并

基于"Scheduler方便处理 + 系统自动处理"原则，合并的前提是：**现场可以一起生产、一起追踪、成本可以合理分摊**。否则必须拆分。

---

## 二、Job优先级策略（问题1的回答）

### 2.1 多SO合并后的Job优先级

```
Job优先级 = MAX(关联Demand的原始优先级) + 业务加权
```

| 场景 | 优先级计算 | 说明 |
|------|-----------|------|
| 单SO单Demand | 继承SO优先级 | 直接映射 |
| 多SO合并（仅MTS） | MAX(SO-A优先级, SO-B优先级, ...) | 生产一旦合并就是同一批，按最紧急的处理 |
| MTO Job | SO优先级 + MTO加权(+10) | 客户专属，必须按期 |
| 返工Job | 最高优先级（自动置顶） | 阻塞原Job关闭，必须插队 |
| 紧急插单 | 手动置顶 或 自动MAX+20 | Scheduler可一键置顶 |

**关键原则：合并生产 = 统一优先级，不可在Job内部再分先后。**

### 2.2 MTO绝对不能跨SO合并

MTO的本质是"专属库存"——每个单位在物理上都属于特定客户。

- ✅ MTO可以和同SO的其他MTO合并（同一客户的多个行项目）
- ❌ MTO不能和不同SO的MTO合并（客户A的产品和客户B的产品不能混批）
- ❌ MTO不能和MTS合并（否则完工后无法区分专属库存和通用库存）

**结论：MTO始终独立成Job，出现在Schedule页面里，Scheduler可见但不可将其与其他SO合并。**

### 2.3 Process（工序）是否拆分？

合并后的Job在现场是**同一批物料、同一套BOM、同一组设备**，因此：

- **Process不拆分**：生产班组按Job统一执行工序
- **但完工时需要分配**：系统按各SO的数量比例或优先级，将完工数量分配回各SO
- 如果不同SO的质量标准不同（如A客户要全检、B客户抽检），则**不可合并**

## 三、Demand合并/拆分规则矩阵（问题2的回答）

### 3.1 规则总览

| Demand来源 | 合并策略 | 是否进Schedule页面 | 理由 |
|-----------|---------|-------------------|------|
| SO - MTS部分 | ✅ **自动合并**（同产品+Site+时间窗） | ✅ | 通用库存，无需客户追溯 |
| SO - MTO部分 | ❌ **必须独立Job** | ✅ | 客户专属，物理不可混批 |
| 返工 Rework | ❌ **独立Job**（或原子任务） | ✅（标记红色） | 流程特殊，质量隔离，最高优先级 |
| 销售预测 Forecast | ⚠️ **只合并，不独立驱动** | ⚠️ 可见但不可单独排程 | 预测=计划参考，必须绑定真实SO或Replenishment才生效 |
| 样品/试制 | ❌ **独立Job** | ✅（标记紫色"样品"） | 成本归集到研发/销售费用，不走标准库存 |
| SO变更增量 | 🔶 **系统建议，Scheduler确认** | ✅ | 未开工→合并；已开工→新建Job |
| 紧急插单 | 🔶 **Scheduler手动决定** | ✅（标记红色"紧急"） | 可能打断当前计划，必须人工确认 |
| 安全库存预警 | ✅ **并入Replenishment** | ✅（系统自动生成） | 纯库存驱动，无客户绑定 |
| Transfer | ❌ **独立Job** | ✅ | 跨Site，本质是"搬运"不是"生产" |
| Replenishment | ✅ **自动合并同类** | ✅（草稿态，待Scheduler确认） | 系统规则驱动，批量确认 |

**图例：**
- ✅ 自动处理
- ❌ 强制独立
- 🔶 需要Scheduler决策
- ⚠️ 特殊处理

### 3.2 合并的触发条件（系统自动）

系统只有在以下**全部满足**时才自动合并：

1. **同一Part Number**（产品/物料相同）
2. **同一Site**（在同一工厂生产）
3. **同一BOM版本**（工艺路线相同）
4. **时间窗重叠**（计划开工日期在±N天内，N可配置，默认7天）
5. **无客户专属约束**（都不是MTO，或都是同一SO的MTO）
6. **质量要求兼容**（各SO的质量标准不冲突）

### 3.3 不可合并的硬性红线

只要满足以下任一条件，**系统强制拆分**：

- 包含MTO且来源SO不同
- 跨Site
- BOM/工艺不同
- 质量标准冲突
- 其中一个是返工/样品
- 其中一个是Transfer

## 四、各类Demand的详细处理逻辑

### 4.1 返工 Rework

```
质检不合格
    │
    ├── 1. 在原Job上标记"异常"，锁定原Job关闭
    │
    ├── 2. 自动创建 Rework Job（或 Rework Sub-task）
    │   ├── 关联原Job编号
    │   ├── 数量 = 不合格数量
    │   ├── 优先级 = 最高（置顶）
    │   └── BOM = 返工工艺路线（可能不同于原BOM）
    │
    ├── 3. Scheduler在Schedule页面看到红色"返工"标记
    │   └── 可调整优先级，但不可与普通Demand合并
    │
    └── 4. Rework完成后
        ├── 合格 → 回到原Job流程，允许关闭
        └── 再次不合格 → 二次返工或报废
```

### 4.2 销售预测 Forecast

Forecast**不直接生成Job**，而是作为"计划建议"：

```
月度Forecast（如：预计下月卖1000件A产品）
    │
    ├── 不直接创建Job（避免无单生产）
    │
    ├── 当真实SO到达时，Forecast参与MTS数量计算：
    │   建议生产量 = SO的MTS部分 + Forecast建议量 + 安全库存缺口
    │
    └── Scheduler在Schedule页面看到"预测参考"列
        └── 帮助判断：这个Job做多少MTS是合理的？
```

**为什么Forecast不单独生成Job？**
- 如果按Forecast生产了但卖不掉 → 库存积压
- Forecast只提供"建议量"，最终生产决策由Scheduler根据真实SO+库存+交期综合决定

### 4.3 样品/试制

```
研发/销售发起样品需求
    │
    ├── 1. 创建独立Job，标记"样品"
    │   ├── 成本归集到研发项目/销售费用
    │   ├── 完工不入标准库存（入样品库或直发客户）
    │   └── BOM = 样品配方（可能不同于量产品）
    │
    ├── 2. 进入Schedule页面（Scheduler必须看见产能占用）
    │   └── 显示为紫色，不参与自动合并
    │
    └── 3. 样品通过后，可能转化为正式SO
        └── 此时创建新的正式Job，不关联样品Job
```

### 4.4 SO变更/紧急插单

```
SO变更（增量+50件 或 交期提前）
    │
    ├── 1. 系统创建"变更Demand"，关联原SO
    │
    ├── 2. 系统自动判断：
    │   ├── 原Job状态 = 草稿/已排程（未开工）
    │   │   └── ✅ 建议：合并到原Job，更新数量/交期
    │   │
    │   └── 原Job状态 = 执行中/部分完成
    │       └── ✅ 建议：创建新Job（追加生产）
    │
    └── 3. Scheduler确认或覆盖系统建议
        └── Schedule页面显示"变更"标记，一键确认

紧急插单（全新SO，交期极短）
    │
    ├── 1. 创建Demand，自动标记"紧急"
    │
    ├── 2. 系统尝试合并到现有Job（如果条件满足）
    │   └── 但通常紧急插单交期特殊，不满足时间窗条件
    │
    └── 3. 独立成Job，Scheduler决定是否：
        ├── 正常排程（按优先级自然竞争）
        ├── 置顶插队（打断现有计划）
        └── 外协处理（自己来不及就委外）
```

### 4.5 安全库存预警 / Replenishment

```
库存低于安全线
    │
    ├── 1. 系统生成 Replenishment Demand
    │   ├── 数量 = 建议补货量（可配置公式）
    │   └── 优先级 = 系统默认中优先级
    │
    ├── 2. 系统自动匹配可合并的Demand（同产品+Site）
    │   └── 如：SO的MTS部分 + 安全库存 = 一个Job
    │
    └── 3. Scheduler批量确认
        ├── 全自动模式：系统直接释放，Scheduler每日复核
        └── 半自动模式：Scheduler批量勾选后释放
```

## 五、Scheduler工作流（合并/拆分视角）

```
所有Demand进入Demand池
    │
    ├── 系统预处理（自动分类+标记）
    │   ├── MTO → 红色标记，不可合并
    │   ├── 返工 → 深红标记，置顶
    │   ├── 紧急 → 闪烁标记，高亮
    │   ├── 样品 → 紫色标记，不可合并
    │   └── 普通MTS/Replenishment → 白色/灰色标记
    │
    ├── 系统自动尝试合并（按6条件）
    │   ├── ✅ 满足条件 → 合并为Candidate Job
    │   └── ❌ 不满足 → 保持独立Demand
    │
    ├── Scheduler审阅Schedule页面
    │   ├── 查看系统自动合并建议
    │   ├── 可手动拆分（如：虽然可合并，但Scheduler认为应该分开）
    │   ├── 可手动合并（如：系统未识别但Scheduler认为可以）
    │   └── 确认优先级（系统建议，Scheduler可调整）
    │
    └── 确认后的Job进入Site Plan
        └── 各Site按Job执行
```

## 七、仍需用户确认的3个关键问题

1. **Site Plan能否调整Scheduler已排顺序？**
   - 严格模式：Site只能标记状态，不能改顺序
   - 灵活模式：Site可调整本Site内顺序，同步回Scheduler

2. **Transfer是否计价？**
   - 不计价：内部调拨，仅记录数量
   - 计价：按标准成本转移，影响各Site利润核算

3. **Scheduler排程周期？**
   - 实时：Demand进入立即可见，Scheduler随时处理
   - 日清：每日固定时间（如早上8点）批量排程
