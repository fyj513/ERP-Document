# PRAM3 前端开发规范手册

  

  

## 核心规则

  

  

**零依赖政策**：交付产物不得包含任何第三方运行时库（React、lodash、axios 等）。ESLint、Prettier 等开发工具仅在开发和 CI 阶段使用，不进入交付产物。

  

  

**语言规范**：代码中所有 JSDoc 注释和测试描述必须用**英文**。中文出现在注释或测试描述中，Code Review 直接驳回。

  

  

---

  

  

## 第1章 目录结构

  

  

```

  

pram3_corelibs/                ← 仓库根目录

  

├── scripts/

  

│   ├── gen-api-doc.js         ← 共用：从源码注释生成 API 文档

  

│   └── gen-test-doc.js        ← 共用：从测试注释生成测试文档

  

└── Source/

  

    └── HashFunctions/

  

        ├── docs/

  

        │   ├── API_AUTO.md    ← gen-api-doc.js 生成，禁止手动修改

  

        │   ├── TEST_AUTO.md   ← gen-test-doc.js 生成，禁止手动修改

  

        │   └── help.md        ← 本规范手册

  

        ├── src/

  

        │   ├── main.js        ← 唯一入口文件

  

        │   ├── murmur.js      ← 功能模块

  

        │   ├── sha.js         ← 功能模块

  

        │   └── utils.js       ← 内部工具（不暴露给外部）

  

        ├── tests/

  

        │   ├── main.test.js   ← 公开 API 测试

  

        │   └── <libname>.test.js   ← 内部单元测试（以库名命名，如 duration.test.js）

  

        └── package.json

  

```

  

  

**铁律**：

  

- `src/main.js` 是唯一入口，**禁止创建 `src/index.js`**

  

- `docs/API_AUTO.md` 和 `docs/TEST_API_AUTO.md` 由脚本自动生成，**禁止手动修改**

  

- 每个 `src/*.js` 文件不超过 300 行

## 第2章 `src/main.js` 规范

  

  

`main.js` 只做两件事：**Re-export（门卫）** 和 **`@module` 注释**。禁止写任何算法逻辑。

  

  

```javascript

  

// AI-generated: module entry point for HashFunctions library

  

  

/**

  

 * HashFunctions — Non-cryptographic (Murmur) and cryptographic (SHA) hash functions.

  

 *

  

 * All functions accept: string, any TypedArray (e.g. Uint8Array), or ArrayBuffer.

  

 *

  

 * @module HashFunctions

  

 */

  

  

import * as Murmur from './murmur.js';

  

import * as SHA from './sha.js';

  

  

export { Murmur, SHA };

  

```

  

  

**禁止在 `main.js` 出现**：算法逻辑、工具函数、`console.log`、变量声明、手动命名空间对象（如 `export const Libs = { ... }`）。

  

  

> **为什么不手动包命名空间？** 命名空间由构建系统根据 `lib.json` 的 `path` 字段自动挂载。手动包一层会导致重复嵌套。详见下方第2.1章。

  

  

---

  

  

## 第2.1章 `lib.json` 命名空间规范

  

  

构建系统读取 `lib.json` 的 `path` 字段，把 `main.js` 的每个具名导出自动挂到对应路径下。

  

  

```json

  

{

  

    "path": "Libs.Crypto.Hash"

  

}

  

```

  

  

`main.js` 导出 `Murmur` 和 `SHA` 后，构建系统自动生成：

  

  

```

  

Libs.Crypto.Hash.Murmur  ←  Murmur 模块

  

Libs.Crypto.Hash.SHA     ←  SHA 模块

  

```

  

  

**铁律**：`main.js` 只管导出类/模块本身，命名空间路径只在 `lib.json` 里填，两者职责分离。

  

  

---

  

  

## 第2.2章 导出类继承规范

  

  

所有对外导出的 API 类必须继承 `CoreLib`。

  

  

```javascript

  

// AI-generated: inherit CoreLib to comply with library base class requirement

  

import { CoreLib } from '../../coreLib/src/main.js';

  

  

export class MyHashClass extends CoreLib {

  

    // ...

  

}

  

```

  

  

继承链：

  

  

```

  

ClassAsync          ← 提供 .Ready（Promise）和 .IsReady（boolean）异步初始化能力

  

    └── CoreLib     ← 所有库的统一基类（当前为 stub，为未来扩展预留钩子）

  

            └── 各库导出类（如 Murmur、SHA、Duration …）

  

```

  

  

> **为什么要继承 CoreLib 而不是直接写 class？** CoreLib 是未来给所有库统一加功能的扩展点。现在继承它是空操作，但一旦 CoreLib 新增能力，所有库自动获得，无需逐一修改。

## 第3章 源码注释规范

  

  

> **注释是数据，脚本是解析器。** 注释写得规范，`gen-api-doc.js` 才能正确生成文档。

  

  

### 脚本识别规则

  

  

`gen-api-doc.js` 只看注释本身，不关心后面跟的是 `export function`、类方法、getter 还是其他写法：

  

  

| 注释特征 | 脚本行为 |

  

|---|---|

  

| 有 `@example`，没有 `@private` | ✅ 识别为公开 API，生成文档 |

  

| 有 `@private` | ❌ 跳过 |

  

| 没有 `@example` | ❌ 跳过 |

  

  

### 注释与文档的一一对应关系

  

  

```javascript

  

/**

  

 * MurmurHash64A — 64-bit non-cryptographic hash.   ← ① 函数描述

  

 *

  

 * @param {string|...} data - Input to hash          ← ② 参数表格第一行

  

 * @param {number} [seed=0] - Optional seed value    ← ③ 参数表格第二行（可选，No default: 0）

  

 * @returns {bigint} Unsigned 64-bit integer         ← ④ Returns 行

  

 * @example                                          ← ⑤ Example 代码块（必须有，否则脚本跳过）

  

 * const result = mmh2('hello');

  

 * // => 2191231550387646743n

  

 */

  

export function mmh2(data, seed = 0) { }

  

```

  

  

生成的文档片段：

  

  

```markdown

  

### `mmh2(data, seed = 0)`          ← 函数签名（自动从代码提取）

  

  

MurmurHash64A — 64-bit ...          ← ① 描述

  

  

| Parameter | Type       | Required          | Description       |

  

|-----------|------------|-------------------|-------------------|

  

| data      | string\|.. | Yes               | Input to hash     |  ← ②

  

| seed      | number     | No (default: `0`) | Optional seed ... |  ← ③

  

  

**Returns**: `bigint` — Unsigned ... ← ④

  

  

**Example**:                         ← ⑤

  

const result = mmh2('hello');

  

// => 2191231550387646743n

  

```

  

  

### 标准模板

  

  

```javascript

  

/**

  

 * 一句话描述函数做什么（英文）         ← ① 描述

  

 *

  

 * @param {类型} 参数名 - 参数描述      ← ② 参数表格行

  

 * @param {类型} [可选参数=默认值] - 描述 ← ③ 可选参数行

  

 * @returns {类型} 返回值描述           ← ④ Returns 行

  

 * @example                            ← ⑤ Example 代码块

  

 * const result = functionName('hello');

  

 * result;

  

 * // => 具体的返回值（必须真实可运行）

  

 */

  

```

  

  

### 示例

  

  

**同步函数（Murmur）**：

  

  

```javascript

  

/**

  

 * MurmurHash64A — 64-bit non-cryptographic hash.

  

 *

  

 * @param {string|ArrayBufferView|ArrayBuffer} data - Input to hash

  

 * @param {number} [seed=0] - Optional seed value

  

 * @returns {bigint} Unsigned 64-bit integer

  

 * @example

  

 * const result = mmh2('hello');

  

 * result;

  

 * // => 2191231550387646743n

  

 */

  

export function mmh2(data, seed = 0) { ... }

  

```

  

  

**异步函数（SHA）**：

  

  

```javascript

  

/**

  

 * SHA-1 (160-bit).

  

 *

  

 * @param {string|ArrayBufferView|ArrayBuffer} data - Input to hash

  

 * @returns {Promise<string>} 40-character uppercase hex string

  

 * @example

  

 * const result = await sha1('hello');

  

 * result;

  

 * // => 'AAF4C61DDCC5E8A2DABEDE0F3B482CD9AEA9434D'

  

 */

  

export async function sha1(data) { ... }

  

```

  

  

### 注释规则速查

  

  

| 规则 | 说明 |

  

|---|---|

  

| 需求提到的公开函数 | 必须写完整注释（描述、`@param`、`@returns`、`@example`） |

  

| 内部函数 | 只需加 `@private`，脚本自动跳过 |

  

| `// =>` 后面 | 必须是真实可运行的具体值，不能写描述性文字 |

  

| 异步函数 | `@example` 里加 `await` |

  

| bigint 返回值 | 末尾加 `n`，如 `2191231550387646743n` |

  

| 可选参数 | 用方括号 `[seed=0]`，生成"No (default: 0)" |

## 第4章 测试文件规范

  

### 两个测试文件的职责划分

  

测试必须拆成两个文件，分别对应不同的视角：

  

| 文件 | 命名规则 | 测试内容 | 视角 |

|---|---|---|---|

| `main.test.js` | **固定名，不可更改** | 需求里列出的公开 API | 用户视角——对外行为 |

| `<libname>.test.js` | **以库名命名**，如 `duration.test.js` | 标了 `@private` 的内部方法 | 开发者视角——实现细节 |

  

**为什么要拆？** 公开 API 测试关注"结果"，内部测试关注"实现"。内部重构时只要对外行为不变，`main.test.js` 就不应该报错；而内部测试文件允许跟着实现一起改。

  

生成测试文档时两个文件会分开扫描，脚本根据文件名自动打标签——`main.test.js` 标为 **Public API Tests**，其他文件标为 **Internal Unit Tests**：

  

```bash

node ../../scripts/gen-test-doc.js \

    --files tests/main.test.js,tests/duration.test.js \

    --out docs/TEST_AUTO.md \

    --title "Durations Test Specification"

```

## 第4.1章 测试注释规范

  

  

> 注释是数据，脚本是解析器。注释写得规范，`gen-test-doc.js` 才能正确生成测试文档。

  

  

### 注释与文档的一一对应关系

  

  

```javascript

  

/**

  

 * Verify that mmh2 returns a bigint.   ← ① 分组标题 + Description 列

  

 *    ↑

  

 *    └─ "Verify that mmh2" 中的 mmh2 → 生成 ### `mmh2` 分组标题

  

 *       整句话                        → 生成表格 Description 列

  

 *

  

 * @param {string} data - Murmur.mmh2('test')

  

 *                         ↑

  

 *                         └─ ② Input 列

  

 *

  

 * @returns {boolean} typeof result === 'bigint' — Happy Path

  

 *                    ↑                             ↑

  

 *                    └─ ③ Expected 列              └─ ④ Scenario 列

  

 */

  

```

  

  

生成的表格一行：

  

  

| # | Description | Input | Expected | Scenario |

  

|---|---|---|---|---|

  

| TC-001 | Verify that mmh2 returns a bigint. | `Murmur.mmh2('test')` | `typeof result === 'bigint'` | Happy Path |

  

  

### 脚本识别规则

  

  

`gen-test-doc.js` 只看注释本身，不关心后面跟的是具名函数、箭头函数还是其他任何写法：

  

  

| 注释特征 | 脚本行为 |

  

|---|---|

  

| 描述以 `Verify that 函数名` 开头 | ✅ 识别为测试用例，生成文档 |

  

| 描述不以 `Verify that` 开头 | ❌ 跳过 |

  

  

### 标准模板

  

  

```javascript

  

/**

  

 * Verify that 函数名 具体在测什么。        ← ① 必须以 "Verify that 函数名" 开头

  

 *

  

 * @param {类型} data - 调用代码            ← ② Input 列

  

 * @returns {类型} 期望结果 — 场景类型      ← ③ Expected 列 — ④ Scenario 列

  

 */

  

// 后面跟什么代码写法都可以，脚本只认注释

  

runTest('描述', () => { ... });

  

```

  

  

### 关键规则

  

  

**① 描述第一行必须以 `Verify that 函数名` 开头** — 脚本用它来分组：

  

  

```javascript

  

// ✅ 正确

  

/**

  

 * Verify that mmh2 returns a bigint.

  

 */

  

  

// ❌ 错误 — 脚本无法识别函数名，无法分组

  

/**

  

 * mmh2 should return a bigint.

  

 */

  

```

  

  

**④ `@returns` 末尾用 `—` 分隔场景类型**（只能写这三个）：

  

  

```javascript

  

@returns {boolean} typeof result === 'bigint' — Happy Path

  

@returns {boolean} both return equal values — Edge Case

  

@returns {Error} throws an Error — Error Case

  

```

## 第5章 文档自动化

  

  

### 工作原理

  

  

脚本不依赖任何第三方工具，直接读文件、用正则扫注释、输出 Markdown：

  

  

```

  

源码注释 → gen-api-doc.js（正则解析）→ docs/API_AUTO.md

  

测试注释 → gen-test-doc.js（正则解析）→ docs/TEST_API_AUTO.md

  

```

  

  

### 常用命令

  

  

| 命令 | 作用 |

  

|---|---|

  

| `npm test` | 跑所有测试 |

  

| `npm run docs:api` | 生成 API 文档 |

  

| `npm run docs:test` | 生成测试文档 |

  

| `npm run docs:all` | 同时生成两者 |

  

  

脚本路径：`../../scripts/gen-api-doc.js` 和 `../../scripts/gen-test-doc.js`（仓库根目录共用）。

  

  

### 什么时候需要改脚本

  

  

脚本是纯注释驱动的，**绝大多数情况下不需要改脚本**：

  

  

| 情况 | 做什么 |

  

|---|---|

  

| 新增公开函数/方法 | 只需加规范注释（有 `@example`，无 `@private`），脚本自动扫到 |

  

| 新增测试 | 只需注释以 `Verify that 函数名` 开头，脚本自动扫到 |

  

| 新增源码文件或测试文件 | 在 `package.json` 的 `docs:api` / `docs:test` 命令里追加 `--files` 参数即可 |
