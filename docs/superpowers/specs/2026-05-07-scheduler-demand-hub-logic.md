## 一、核心概念重新定义

| 概念 | 定义 | 与旧系统的关系 |
|------|------|----------------|
| **Scheduler** | 公司唯一的"需求处理大脑"。所有需要行动的需求（Demand）在此汇聚，由调度员决定：是否处理、何时处理、在哪个Site处理、用什么方式处理（生产/采购/调拨/委外）。 | 取代传统SO-only的订单处理逻辑，MTO/Transfer/Replenishment不再游离于排程之外。 |
| **Site** | 有独立地理位置或逻辑隔离的生产/仓储单元。每个Site有自己的Plan页面。 | 对应现有库存管理中的 Warehouse/Location，但功能扩展为包含生产能力的"工厂"。 |
| **Job** | 通用执行单元。一旦Scheduler决定处理某个Demand，就创建Job。Job告诉各团队做什么：采购部（买什么）、仓库（收多少/退多少）、生产组（生产什么/BOM/工序）。 | 取代传统割裂的PO、生产工单、调拨单。PO是Job的"采购子任务"，生产指令是Job的"制造子任务"。 |
| **Demand** | 任何触发行动的原始需求。是Schedule页面的"待办事项"。 | 来源多元化：SO、MTO、Transfer、Replenishment、预测、返工等。 |

## 三、关键业务逻辑走查

### 3.1 Job 的构成模型

你说Job"告诉要参与这个需求处理的所有人要干什么"，这个设计很核心。我建议把Job解构为：

```
Job (BOM完全展开后的执行载体)
├── 基础信息
│   ├── Job编号、Site归属、优先级、计划起止时间
│   ├── Demand来源 (SO/MTO/Transfer/Replenishment/...)
│   ├── 顶层产品/物料 (Top-Level Part Number)
│   └── 数量分配：MTS数量 vs MTO数量
│
├── BOM完全展开（多级结构）
│   ├── Level 0: 成品 (Finished Good)
│   │   ├── Level 1: 半成品 A (Sub-assembly)
│   │   │   ├── Level 2: 原材料 A-1 → 采购子任务 / 制造子任务
│   │   │   ├── Level 2: 原材料 A-2 → 采购子任务
│   │   │   └── 工序路线: 下料 → 机加 → 表面处理
│   │   ├── Level 1: 半成品 B
│   │   │   ├── Level 2: 原材料 B-1 → 采购子任务
│   │   │   └── 工序路线: 注塑 → 装配
│   │   └── Level 1: 包装物 → 采购子任务
│   └── 每级BOM节点包含: 需求数量、可用库存、净需求、供应商、工序、标准工时
│
├── 子任务清单 (Sub-tasks) —— BOM展开后逐层生成
│   ├── 制造子任务（按BOM层级生成，每层SFG对应一个MO）
│   ├── 采购子任务（最底层原材料/外购件，对应PO行）
│   ├── 调拨子任务 → 生成Transfer Order
│   ├── 委外子任务 → 生成外协PO
│   └── 退货子任务 → 生成退货单/退款流程
│
├── 状态生命周期
│   └── 草稿 → 已排程 → 执行中 → 部分完成 → 已完成 → 已关闭
│
└── 关联单据
    ├── 来源Demand单号
    ├── 下游PO单号列表（按BOM层级）
    ├── 下游生产工单号列表（按BOM层级）
    └── 下游出入库单号
```

### 3.2 MTS vs MTO 数量分配逻辑

你提到的分配影响，我帮你细化：

| 维度 | MTS 部分 | MTO 部分 |
|------|----------|----------|
| **库存路径** | 生产完工 → 入成品库 → 销售时出库 | 生产完工 → 直接绑定SO/客户 → 不入库或虚拟过账 |
| **成本归集** | 入库存商品科目，按标准成本/移动平均 | 直接归集到SO销售成本，不走库存科目 |
| **排程优先级** | 标准优先级（按交期/库存水位） | **高优先级**（有客户绑定，必须按期） |
| **数量可调整性** | 可基于预测灵活调整 | 严格绑定SO数量，变更需走SO变更流程 |
| **超额生产** | 允许（安全库存策略） | 不允许（客户专属） |

**⚠️ TBD-7：MTS/MTO拆分由谁决定？**
- 选项A：Scheduler人工在排程时分配
- 选项B：系统根据SO配置自动分配（如SO的"专用生产"标志）
- 选项C：产品层配置默认比例，Scheduler可覆盖

### 3.3 MTO 的优先级调控

你问："有没有别的能够调控他优先级的" —— 有，而且需要一套完整的优先级引擎：

```
优先级得分 = f(紧急度, 客户等级, 利润贡献, 交期偏差, 产能匹配)
```

| 调控因子 | 说明 | 调控方式 |
|----------|------|----------|
| **手动置顶** | Scheduler人工标记"紧急" | 绝对优先级，排最前 |
| **客户等级** | VIP客户订单自动加权 | 客户档案配置权重 |
| **交期紧迫度** | 距离承诺交期的剩余时间 | 自动计算：越近越高 |
| **延迟惩罚** | 已延迟订单的惩罚系数 | 每延迟1天，优先级+10 |
| **利润贡献** | 订单毛利/战略重要性 | 高利润订单优先 |
| **产能匹配度** | 当前Site产能与订单匹配度 | 匹配度高的优先（减少换线） |

**⚠️ TBD-8：优先级是单一维度还是多维度加权？**
- 简单模式：高/中/低 三档
- 高级模式：0-100分连续得分，Scheduler可调权重

### 3.4 Site Plan 页面的作用边界

你说每个Site有独立Plan页面，"最重要的作用是标记顺序，还有处理状态"。

我建议明确Site Plan的职责范围：

| 层级 | 页面 | 核心决策 | 用户 |
|------|------|----------|------|
| **公司级** | Schedule（Scheduler） | 哪些Demand值得做、在哪个Site做、用什么策略（MTS/MTO/采购/调拨） | 计划经理/Scheduler |
| **Site级** | Site Plan | 在本Site内，Job的**执行顺序**、产线分配、班次安排、状态跟踪 | 工厂主管/班组长 |

**关键区分：**
- Scheduler决定：**做不做、怎么做、在哪里做**
- Site Plan决定：**什么时候做、哪条产线做、谁先谁后**

**⚠️ TBD-9：Scheduler排程后，Site Plan是否允许调整顺序？**
- 严格模式：Site Plan只能标记状态，不能改顺序
- 灵活模式：Site Plan可调整本Site内顺序，但需同步回Scheduler

### 3.5 Transfer 需求的完整流程

你提到Transfer是"同一公司别的site请求调货的时候，由schedulor创建的"。流程需要补全：

```
需求Site（缺货）          Scheduler中枢           供应Site（有库存）
    │                         │                         │
    │── 1.提交Transfer请求 ───>│                         │
    │   （物料+数量+需求日期）  │                         │
    │                         │── 2.检查全公司库存 ─────>│
    │                         │   （各Site可用量）        │
    │                         │<── 3.返回库存数据 ────────│
    │                         │                         │
    │                         │── 4.创建Transfer Job ────>│
    │                         │   （含出库子任务）         │
    │<── 5.确认Transfer计划 ───│                         │
    │   （预计到货日期）        │                         │
    │                         │                         │── 6.执行出库
    │                         │                         │   （生成出库单）
    │<── 7.收货入库 ───────────│<────────────────────────│
    │   （生成入库单）          │                         │
    │                         │── 8.关闭Transfer Job ────>│
```

**⚠️ TBD-10：Transfer的定价/成本如何处理？**
- 同一公司内，Transfer是否计价？按成本价还是标准价？
- 是否影响各Site的利润核算？

### 3.6 Replenishment 的自动配置规则

你说Replenishment"由系统生成的补货需求，需要自动配置job和po"。

自动触发条件（建议）：

| 触发方式 | 规则 | 生成的Demand |
|----------|------|-------------|
| **安全库存触发** | 可用库存 < 安全库存线 | Replenishment Demand，数量 = 最大库存 - 当前库存 |
| **再订货点触发** | 库存降至再订货点 | Replenishment Demand，数量 = 经济订货批量(EOQ) |
| **缺货触发** | 库存为0且有未满足需求 | 紧急Replenishment Demand |
| **定期补货** | 按固定周期（如每周一） | 周期性Replenishment Demand |

**⚠️ TBD-11：Replenishment生成Job后，是否需Scheduler审批？**
- 全自动：系统直接创建Job并释放给Site
- 半自动：系统创建Job草稿，Scheduler每日批量确认
- 人工：每个Replenishment都需Scheduler审批
